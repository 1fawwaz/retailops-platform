# StockPilot Core API contract

StockPilot Core and RetailOps AI communicate only over HTTP (ADR 001). This
document is the map of what "the contract" is, where it lives, how it's
frozen, and what breaks it — the mechanism ADR 001 calls out as the thing
that stops the agent silently breaking when the environment changes.

## What's frozen, and where

| Path | What it is |
|---|---|
| `contracts/stockpilot-api/versions/v1.json` | The full OpenAPI 3.1 document for the current API version, frozen. This is the source of truth the contract test compares against. |
| `contracts/stockpilot-api/schemas/<operationId>.json` | One self-contained JSON Schema per endpoint response (request bodies aren't split out separately; they're inside `v1.json`), for browsing a single endpoint's shape without wading through the full document. Every `$ref` is resolved and bundled locally into `$defs`, so any one file is enough on its own to validate a response against. |

Both are generated by `stockpilot-core/scripts/export_contracts.py`, which
introspects the live FastAPI app's `openapi()` output — it does not hand-write
schemas, so it can't drift from what the app actually returns at export time.

## Why version v1 only

This is a single-consumer contract (RetailOps AI is StockPilot Core's only
client) inside one repository, not a public API with independent release
trains. There is exactly one frozen version because there has been exactly
one Stage 1 milestone that calls for freezing it. If the API needs a breaking
change after RetailOps AI (Stage 2+) depends on it, that's the point at which
a `v2.json` gets added alongside `v1.json` — not before, since a versioning
scheme with only one version ever populated is speculative machinery, not a
real need yet.

## The contract test

`stockpilot-core/tests/test_contracts.py` runs on every `pytest` invocation
(so on every CI run, per Task 6's own coverage/CI requirements) and checks
three things:

1. `contracts/stockpilot-api/versions/v1.json` exists.
2. The live app's `app.openapi()` output equals what's frozen in `v1.json`,
   byte-for-byte after JSON parsing (dict equality, not a diff heuristic).
3. Every file in `contracts/stockpilot-api/schemas/` matches what
   `scripts/export_contracts.py` would regenerate for that endpoint today,
   and there's exactly one file per current endpoint (no orphaned files for
   endpoints that no longer exist, no missing files for new ones).

A fourth check, `test_every_response_schema_declares_at_least_one_example`,
enforces the "OpenAPI examples on every endpoint" requirement structurally,
not just by convention — a new response model without an example fails CI
the same way a drifted contract does.

**This test was deliberately verified to fail, not just written to pass.**
During Task 6, the frozen `v1.json` was tampered with (a field renamed) and
`pytest` was re-run to confirm `test_live_openapi_schema_matches_frozen_contract`
actually catches it, before the real frozen file was restored. A contract
test nobody has ever watched fail is not evidence it works.

## What re-freezing looks like

1. Change a response/request Pydantic model (add a field, rename one, change
   a type) in `stockpilot-core/schemas/`.
2. `pytest` fails on `test_contracts.py` — this is the intended behavior,
   not a bug to work around.
3. Review that the schema change is actually intended (this is the point
   where an accidental breaking change gets caught, before it reaches an
   agent built against the old contract).
4. Run `python scripts/export_contracts.py` from `stockpilot-core/`.
5. Review the diff in `contracts/stockpilot-api/` like any other code change
   — it's a real artifact, not generated-and-forgotten.
6. Commit the refreshed contract in the same commit as the schema change, so
   the two never land separately.

There is currently no automated "did you mean to break this" gate beyond the
failing test itself — a human has to look at the diff and decide the change
is intentional. That's deliberate at this project's size: an automated
semver-bump-detector would be more machinery than the one-consumer,
one-repository reality currently justifies.

## What this doesn't cover

- **Request validation contracts** (query parameter constraints, path
  parameter types) live inside `v1.json` as part of the full OpenAPI
  document, but aren't broken out per-endpoint the way response schemas are
  — the per-endpoint files under `schemas/` are response-shape-focused,
  matching Task 6's own wording ("JSON Schema per endpoint").
- **Runtime behavior** (what a 404 vs. a 422 means, rate limits, auth
  scopes) isn't schema-expressible and isn't attempted here; it's documented
  in code (`api/deps.py`, each router) and exercised by the ordinary test
  suite, not the contract test.
- **The agent's generated client** (Stage 2, `retailops-ai/`) is out of
  scope for this document — it consumes `v1.json` but its own generation
  step and typed wrapper are Stage 2 work, not Stage 1's.
